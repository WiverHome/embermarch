# Embermarch — идеи и задачи на будущее

Заметки для возврата позже. Записано 2026-09-27, обновлено 2026-10-01 (двадцать седьмой проход).

## Сделано 2026-10-01 (Шесть доработок после перехода на главы — двадцать седьмой проход)

Владелец выбрал сразу шесть направлений одним списком после вопроса «что ещё
можем добавить»; закрыты все шесть.

- **Сюжетная связка между главами**: новый `CHAPTER_ARRIVAL` + функция
  `maybeShowChapterTransition()` — модалка с парой строк атмосферного текста
  (что остаётся позади, что начинается впереди) при входе в новую главу,
  вызывается из `finishRewardNode()` сразу после победы над боссом главы
  (`node.layer!==TOTAL_MAP_LAYERS`, то есть не финальный босс). Не влияет на
  механику, закрывается одной кнопкой «Вперёд».
- **Биом-специфичные событийные цепочки**: у объекта события появилось
  необязательное поле `biome`; `startEvent()` при выборе нового (не
  цепочечного) события фильтрует пул по `biomeKeyForLayer(node.layer)`,
  событие без `biome` остаётся общим. Уже начавшаяся цепочка (через
  `RUN.pendingChainEvent`) продолжается независимо от смены биома — иначе
  игрок мог бы зайти в Мороз с незакрытой пепельной цепочкой. Привязаны к
  Пепельному походу 4 существующих события с огненным текстом (idol/ashes/
  forge/wardstone). Добавлены 2 новые цепочки: «Ледяной курган →
  Холод кургана» (Морозный рубеж) и «Плачущий цветок → Цветок прорастает»
  (Терновая чаща), зеркальные по структуре существующим цепочкам.
- **Ширина экрана карты на десктопе**: владелец прислал скриншот — на
  1920px-экране видно только ~2 яруса из 4, при этом вся остальная ширина
  пустует (карта всё ещё горизонтально скроллится, т.к. `#app` держит общую
  колонку в 860px на всех экранах). При `min-width:960px` `#screen-map`
  (и `#topbar`, пока виден именно экран карты — через `:has()`) теперь
  «выламывается» из обычной колонки до `min(94vw,1360px)` стандартным
  приёмом full-bleed (`position:relative;left:50%;transform:translateX(-50%)`).
  Мобильная раскладка (≤680px, отдельный вертикальный список узлов) не
  затронута. Видно 4 яруса вместо 2 без прокрутки.
- **Живой PvP на полный состав**: раньше `live-pvp.js` на сервере брал только
  `heroes[0]` из сохранённого чемпиона (у клиента такого ограничения не было
  — асинхронная арена уже посылала весь состав 1-3 героя). Это было чисто
  серверное ограничение: `instantiateCombatant`/`buildTurnOrder`/
  `getValidTargets`/`applyAbilityEffect` в `combat-engine.js` уже работали по
  спискам `state.party`/`state.enemies` без единого жёсткого индекса `[0]`
  (тот же движок используется и в обычном PvE-бою на 3 героя). Правка:
  `loadChampion()` отдаёт весь массив, `createDuelState(championsA,
  championsB)` строит обе стороны по массивам (с обратной совместимостью —
  принимает и одиночный чемпион, оборачивая в массив). Бэкенд-файлы
  (`live-pvp.js`, `combat-engine.js`) отправлены владельцу отдельным zip для
  самостоятельного деплоя — репозиторий не хранит рабочую копию `server/`
  актуальной (бэкенд живёт на VPS, обновления не коммитятся).
- **Летопись — вкладки/аккордеон**: при проверке оказалось, что это уже
  реализовано в прошлых проходах (`.legacy-tabs`/`.legacy-tab-panel`, 4
  вкладки: Прокачка/Сложность/Статистика/Настройки) — отдельной работы не
  потребовалось, только подтверждение скриншотами.
- **Пятая ветка дерева улучшений — «Благосклонность фортуны»**: первая ветка
  не про плоскую характеристику героя, а про экономику похода. База
  `fortune` (макс. 3, +2%/ур.) → обряд `fortune_rite` (макс. 2, +3%/ур.,
  требует `fortune` ур.3) → вершина `fortune_capstone` (+10% одним куском +1
  осколок при разборе снаряжения, требует `fortune_rite` ур.2). Новая
  функция `relicChanceBonus()` — единая точка подсчёта, применена во всех
  трёх местах, где раньше был зашит шанс реликвии: награды похода
  (`buildRewardCards`, было 16%), ассортимент лавки (`buildShopStock`, было
  25/40/60% по ярусу), выход осколков при разборе (`salvageYield`). На
  максимум даёт +22 процентных пункта — заметный, но не ломающий баланс
  поздний бонус за ~130 угольков суммарно по всем трём уровням ветки,
  сравнимо по цене с другими вершинами.
- Проверено по каждому пункту: `node --check`; для сюжетной связки и
  биом-событий — скриптовый аудит EVENTS (все id уникальны, все
  `pendingChainEvent`-ссылки существуют, биом-теги на нужных событиях) плюс
  пересчёт `biomeKeyForLayer` для всех слоёв; два Playwright-прогона
  авто-боем до босса первой главы (без ошибок, одна цепочка событий
  сработала по пути); для карты — скриншоты 1920×1000 до/после (4 яруса
  вместо 2) и регрессия на остальных экранах + мобильном 390×844
  (пиксель-в-пиксель без изменений); для живого PvP — два теста на реальном
  поднятом сервере (`test-livepvp.js` — старые 1v1-сценарии не сломаны;
  новый `test-livepvp-squad.js` — 3v3, подтверждён реальный бой 6 разных
  юнитов, а не 2); для ветки Фортуны — скриншот Летописи с новой веткой,
  отдельный клик-прогон списка улучшений без ошибок в консоли.

## Сделано 2026-10-01 (Биомы стали последовательными главами — двадцать шестой проход)

- Поход больше не «выбери один из трёх биомов на старте» — теперь это всегда
  один маршрут, проходящий через все три земли по возрастающей сложности:
  Пепельный поход → Морозный рубеж → Терновая чаща. В конце первой и второй
  трети похода — босс-кульминация своей главы (обычный враг на пути, не
  останавливает поход при победе), в самом конце — финальный босс Терновой
  чащи.
- Деление идёт по слоям карты: 19 обычных слоёв режутся на трети (CH1=6,
  CH2=13), на этих двух слоях гарантированно один узел — босс главы (та же
  механика, что раньше была только у финального босса). Перед каждым из трёх
  боссов гарантирован узел лавки.
- Сила и вид босса подбираются по слою конкретного узла, а не по концу всего
  похода — поэтому босс первой главы ощутимо слабее финального, а не
  «боссом по эндгейм-силе слишком рано».
- Достижения за конкретных боссов (Колосс/Страж/Сосуд/Ледяной государь)
  раньше проверяли «это был финальный босс похода» — с тремя боссами за
  поход это стало бы невозможным для первых двух глав. Теперь достижение
  засчитывается, если этот босс был побеждён в любой точке похода (и поход
  в итоге выигран). Заодно добавлено недостающее достижение за Тернового
  государя.
- Убран выбор биома на экране выбора героев (выбирать больше нечего) —
  вместо него превью маршрута «1. Пепельный поход → 2. Морозный рубеж →
  3. Терновая чаща».
- Проверено: `node --check`; Node-скрипт пересчитал деление по слоям для
  всех 20 индексов — границы глав и финальный босс оказались ровно там, где
  задумано; Playwright-прогон с авто-боем дошёл до босса первой главы ровно
  на слое 6, встретил его как обычный бой (без ложной немедленной победы),
  без единой ошибки за 289 шагов.

## Сделано 2026-10-01 (Бот для игровых прогонов + найденный краш — двадцать пятый проход)

- Написан Playwright-бот, который реально играет целые прогоны (а не просто
  жмёт первый попавшийся вариант): цель по наименьшему HP, лечение при
  HP союзника <40%, случайный выбор среди доступных способностей вместо
  всегда первой — чтобы потрогать больше билдов/веток, чем старый тупой
  автотест.
- **Найден и исправлен реальный краш**: быстрый повторный клик по панели
  способностей сразу после хода героя мог попасть в окно 250–450 мс, где
  старые кнопки способностей ещё оставались в DOM и кликабельны, хотя
  `RUN.combat.activeHero` уже обнулён — падало с `Cannot read properties
  of null (reading 'side')` и бой зависал (ход не продвигался дальше).
  `resolveHeroAbility()` теперь сразу вызывает `renderActionPanel()`
  (раньше — только `renderCombat()`), плюс защитная проверка в начале
  `heroChooseAbility()`. Проверено: 9 прогонов ботом (бой/события/лавка/
  привал, оба биома) без падений после фикса, два из них дошли до полного
  поражения отряда штатно (без зависания).
- Баланс на свежем аккаунте без вложений в Легаси: при вменяемой игре бот
  стабильно гибнет на слоях 7–8 из 20 (из 2 завершённых до конца прогонов).
  Похоже на ожидаемую кривую сложности для первых заходов (экономика
  угольков и так рассчитана на 9–11 побед до максимума улучшений), но
  стоит держать в уме при следующей живой игре — если это будет
  подтверждаться стабильно и на уже прокачанном аккаунте, тройка
  Брам/Саэль/Ивана/Кест без лекаря первой линии может перекашиваться в
  сторону "здоровье лекаря = смерть отряда" на быстро нарастающей
  сложности.

## Сделано 2026-10-01 (Аудио и портреты героев — двадцать четвёртый проход)

- **Звуки боя**: вместо одиночных осцилляторных «пиков» Web Audio в
  рантайме — 12 заранее синтезированных MP3-файлов (`audio/*.mp3`):
  несколько слоёв гармоник + шумовые транзиенты + небольшой алгоритмический
  «каменный» реверб-хвост + мягкая сатурация. Сгенерированы офлайн
  (numpy/scipy синтез → WAV → MP3), без сэмплов и стороннего материала.
  В игре подгружаются и декодируются через `decodeAudioData`, кэшируются в
  `SFX_BUFFERS`; старый осцилляторный код сохранён как `SFX_FALLBACK` на
  случай, если файл ещё не загрузился или не смог загрузиться.
- **Портреты героев**: вместо одноцветных абстрактных эмблем —
  детализированные SVG-портреты силуэтом бюста с классовыми деталями
  (рога/капюшон/оружие/аксессуар на каждого героя), тёмная заливка для
  контраста на цветном фоне-круге героя, мелкие акценты в его собственном
  цвете. Только значения `HERO_ICON_SVG` изменены, остальная вёрстка/логика
  не тронута.
- Проверено: `node --check` на извлечённом скрипте проходит без ошибок;
  аудио проверено через Playwright мониторингом сетевых запросов (все 12
  файлов грузятся 200, без console/page ошибок) на реальном UI-переключателе
  звука; портреты проверены на экране выбора героя (все 8, включая 4
  заблокированных) и отдельно на реальных боевых размерах аватара
  (36px десктоп / 24px мобильный `.unit-avatar`) — все остаются читаемыми.

## Сделано 2026-10-01 (Мобильный UX-проход — двадцать третий проход)

- **Журнал боя**: убран с мобильного экрана боя (не помещался и не читался),
  вместо этого полный журнал последнего боя доступен после его окончания
  (кнопка на экране победы/поражения/итога арены).
- **Кнопки действий в бою**: на мобиле перенесены вниз экрана, в зону
  большого пальца (CSS `order` внутри `.combat-zone` через
  `display:contents` на `.combat-left`).
- **Экран профиля**: заменил кривую строку «Вы вошли как X / Выйти» на
  титульном экране отдельной кнопкой-профилем со сменой логина и пароля.
  Новые серверные эндпоинты `PUT /api/account/username` и
  `PUT /api/account/password` (оба требуют текущий пароль; смена логина
  переподписывает JWT).
- **Починены товары у торговца**: `RUN.shopStock` был один объект на весь
  поход — теперь `RUN.shopStockByNode[node.id]`, у каждой лавки свой набор.
- **Порядок ходов на мобиле**: иконки растянуты на всю ширину карточки
  (`align-items:stretch` чинил схлопывание дочерних карточек в
  `.combat-zone`) и укрупнены (27→38px, шрифт 11→14px).
- **Карта на мобиле**: вместо горизонтально скроллящейся SVG-карты
  (~2300px шириной, тап-цели ~32px) — вертикальный список только реально
  достижимых узлов как крупные карточки, плюс компактная история
  пройденного. Переключение карта/список — чистый CSS media-query
  (`.map-wrap` / `.map-mobile`), десктоп не тронут.
- **Бой на мобиле «лицом к лицу»**: передний/задний ряд внутри каждой зоны
  теперь колонки, а не строки (`zone-label` на всю ширину через
  `flex-basis:100%`, два `.unit-row` — колонки `flex:1`), с порядком,
  который ставит передний ряд отряда и передний ряд врагов друг напротив
  друга через разрыв между зонами.
- **Угольки**: `computeEmbers()` на поражении/отступлении раньше платил
  почти как за победу (`cleared*2 + ascension*3`, без штрафа) — можно было
  быстро фармить дешёвые нонкомбат-узлы и сливаться. Теперь на поражении
  награда ограничена `min(cleared,6) + ascension*1.5`, заметно ниже честной
  победы.
- Проверено Playwright-ом на 390×844 (и 700/650 по высоте): во всех
  затронутых экранах реальное переполнение (`scrollHeight` vs
  `clientHeight` после сброса скролла) равно нулю; десктоп-вёрстка не
  регрессировала (SVG-карта и вертикальный стек боя остались как были).
  Экраны лавки/события/привала отдельно проверены — уже были полноширинными
  карточками в стопке, правок не потребовалось.

## Сделано 2026-10-01 (Живой PvP в реальном времени — двадцать второй проход)

- Реализован сам «следующий шаг», описанный ниже после двадцать первого
  прохода: живой PvP, сервер — полный арбитр боя.
  `server/combat-engine.js` — честный порт боевого движка клиента на Node
  (не переупрощённая версия: та же `dmgCalc`, все комбо-метки, реликвии,
  тиканье статусов), `server/live-pvp.js` — WebSocket-комнаты, очередь
  подбора + приглашения по коду, ход-за-ходом цикл с таймаутом на ход.
  Клиент переиспользует существующий экран боя целиком
  (`RUN.combat.isLivePvp`, по образцу `RUN.combat.isArena` асинхронной
  арены) — новых экранов боя нет, только карточка «⚔ Живая дуэль» рядом с
  асинхронной на экране Арены. Общий рейтинг (та же таблица `champions`,
  тот же Эло) для обоих режимов PvP.
- Проверено: 20 ботовских дуэлей через голый движок (без сети), прямой
  WebSocket-прогон (очередь/приглашение/техпоражение, два реальных
  аккаунта), и полный Playwright-прогон в двух независимых браузерных
  контекстах через настоящий UI (оба пути поиска соперника, от логина до
  возврата на экран Арены с обновлённым рейтингом).
- Осознанно НЕ сделано (возможные следующие шаги): полноценный «отряд на
  отряд» в живом режиме (сейчас дуэль — всегда первый герой сохранённого
  состава, как и раньше для 1v1-сценария; движок уже умеет multi-unit team,
  не хватает только UI выбора полного состава для живого боя); зрители
  /история прошедших живых боёв; отдельный рейтинг для живого режима, если
  владелец решит, что общий с асинхронной ареной — не то, что нужно.

  времени, который владелец тоже хочет в перспективе. Потребует: боевые
  комнаты на сервере (WebSocket или polling), синхронизацию ходов между
  двумя живыми клиентами, и — самое важное — перенос проверки ходов на

  арена специально спроектирована так, чтобы её можно было не выбрасывать:
  те же данные чемпиона (снимок состава) подойдут и живому режиму.
